## 三处诚实记录

### ① 我推翻了自己写下的一个错误断言

我在 `beat.js` 的初版注释里写："`i * interval` 会累积浮点误差，第 100 拍就漂移几毫秒，必须逐拍累加。"

**实测证明这是错的**（BPM=137、第 2000 拍）：

```
i * interval 末值 = 875474.4525547446
逐拍累加     末值 = 875474.4525547397
差值 = 4.89e-9 ms
```

纳秒级，比 1ms 小 20 万倍。而且 `i*interval` 反而**略准** —— 乘法把 interval 的舍入误差一次性摊掉了，反复加则每次都带一次舍入。

代码仍保留逐拍累加，但**理由已改成真实的两条**（为将来支持 swing/变拍速；可读性不易写错下标），并明确写下"若将来有人改成 `i*interval`，不要以'修正精度错误'为理由 —— 没有错误可修"。

测试同步改写：新增一条专门**记录这个实测结论**（两算法差异 <1e-6ms），改写任一方导致差异变大就会红。

### ② 测试数据写错，差点误判成产品 bug

我最初写「打 1.23s、节拍 1.25s、容差 50ms → 应命中」，用 BPM=120 生成网格后返回 `null`，一度以为是二分查找写错了。

手工推演才发现：**BPM=120 的拍点是 0/500/1000/1500…，1.23s 离最近拍点有 230ms，本就不该命中。** 是我的测试数据自相矛盾。

修法：改用「第一拍偏移 250ms」的网格，拍点变成 250/750/1250…，1.25s 才真的是拍点 —— 这才是"用户打在拍点附近"的真实场景。

顺带**补了一条反向用例**：`BPM=120 时 1.23s 离最近拍点 230ms → 不该命中`，防止未来有人把吸附做得过宽。

### ③ 顺手修了一个真实的产品缺陷（在本步范围内）

`Number('')` 和 `Number(null)` 都等于 `0`。原实现里空输入会掉进「BPM ≤ 0」分支，报出 **"BPM 必须大于 0"** —— 而用户看到的现象是**输入框是空的**。报错与现象对不上，用户会以为自己填了个 0。

已单独处理空值，报「请输入 BPM」。这属于第 1 步自身的校验器职责，不是"顺手优化"。

## 需要你决定的点

**只有一个，且不阻塞下一步：**

**吸附容差 50ms 是否合适？** 这是我按你之前确认的默认值实现的，但实测显示：
- BPM=120（一拍 500ms）时，50ms = **1/10 拍** —— 合理
- BPM=90（一拍 667ms）时，50ms ≈ 1/13 拍 —— 合理
- BPM=200（一拍 300ms）时，50ms = **1/6 拍** —— 偏宽，可能吸到用户不想改的拍点

要不要改成**按拍数比例**（如固定吸附到 1/12 拍）？还是保持固定 50ms？

我的建议：**先保持 50ms**，等你真机试过再定 —— 这个值靠算不如靠手感。
