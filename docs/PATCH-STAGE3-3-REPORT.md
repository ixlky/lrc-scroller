## 1.3 规范依据（我查了 Pointer Events 规范原文）

规范原文（"Firing events using the PointerEvent interface"一节）：

> If the event is `pointerdown`, the associated device is **a direct manipulation device**, and the target is an Element, then **set pointer capture** for this PointerEvent/pointerId … (implicit pointer capture)

即**隐式捕获只发生在 direct manipulation device（触摸/笔）**，鼠标并不属于这一类。这与你的表述相反，但结论反而更有意义：

**我们的显式 `setPointerCapture` 与真机鼠标的路径产生了冲突，而笔因为走隐式捕获、反而把我们的调用"吸收"掉了。**

无论确切机制如何，你的修复方向是对的，理由是第一性的：

1. **window 监听已覆盖"指针在元素外"的场景**（此前测试 4 已实测证明：拖出元素外/窗口外松手，落点正确）
2. **笔不带显式捕获也完全正常**，反证捕获不是必需的
3. 三次 bug 都与捕获相关

## 1.4 修复：删除 setPointerCapture / releasePointerCapture

按你的方案，把 `attachPointerDrag` 里的两个调用**连同相关注释一起删掉**。

删掉后剩余逻辑正好是全部必要的部分：

```
pointerdown → 在 window 上挂 pointermove/pointerup/pointercancel
    → pointermove 算比例并回调（坐标非法返回 null，不返回 0）
    → pointerup 以事件坐标确定落点
    → pointercancel 沿用当前位置（但必须收尾）
    → 收尾按登记表从 window 解绑（幂等）
```

## 1.6 顺带发现并修掉的一个真 bug：灰阶上拖色相环毫无反应

在写三种指针类型的测试时发现（三个类型都失败，所以不是指针类型问题）：

**从灰阶颜色（如默认的 `#ffffff` 或 `#808080`，饱和度 0）拖色相环，颜色完全不变。**

诊断结果（拦截引擎调用）：

```
组件内部 HSL 状态: ["128","128","128","90°","0%","50%"]   ← H 确实变成 90° 了
拦截到的 set('color.active') 调用: ["#808080"]            ← 也确实写回了
```

**H 变了、写回也发生了，但颜色没变** —— 因为饱和度是 0，`hslToRgb(90°, 0%, 50%)` 数学上就是 `#808080`。我在测试里补了三条单测证明这是数学必然：

```
hslToHex(0,0,50)   === '#808080'
hslToHex(90,0,50)  === '#808080'
hslToHex(240,0,50) === '#808080'   ← 全部相同
```

**修复**：在灰阶上拖色相环时自动把饱和度提到 15%（专业调色器的通行做法）。
取 15% 而非更小的原因：太低（如 3%）在深色背景上几乎看不出颜色，用户仍会觉得"没反应"；太高会破坏用户原有的明暗感觉。已在用彩色时**不动**用户的饱和度。

# 第二部分：虚化跟随用户视角

## 2.1 实现方式

| 需求 | 实现 |
|---|---|
| 虚化引擎接受"中心行"参数 | `computeRenderOpacities(lines, activeIndex, cfg, base, centerIndex)` 新增第 5 参，默认等于 activeIndex（向后兼容） |
| 自动跟随时中心=播放行 | `useAutoScroll` 新增 `centerIndex` computed：`userScrolling=false → activeIndex` |
| 用户滚动时中心=视口中心行 | `userScrolling=true → findRowAtViewportCenter(rowMetrics, currentOffset, containerHeight/2 二分查找)` |
| 停止滚动 3 秒恢复 | 复用既有 `userScrolling` 的 3 秒恢复定时器，无需新代码 |

`findRowAtViewportCenter`（`core/scroll.js`，O(log n) 二分）：

```
轨道位移 offset 表示轨道被向上推了 offset 像素
→ 屏幕视口中心对应的轨道内位置 = offset + containerHeight / 2
→ 在行几何数组里二分查找该位置落在哪一行
```

**性能**：结果只依赖 `userScrolling` 与 `currentOffset`，做成 computed 后，**同一行内滚动时结果不变 → 虚化缓存键不变 → 命中缓存不重算**。实测见 2.3。

## 2.2 你明确的边界语义，已按你说的实现

> "在用户滚动模式下，当前正在播放的那一行不保持 opacity = 1。虚化中心在哪个行，那个行才是实体中心。当前播放行的"突出"由 is-active 类负责（放大、变色），不需要靠 opacity。"

实现上做了一个关键区分：
- **中心行**强制 opacity = 1（`computeRenderOpacities` 末尾的兜底改为作用于 `centerIndex` 而非 `activeIndex`）
- **activeIndex 不再强制为 1** —— 用户回看时，正在播放的行如果距离中心很远，就按自己的距离正常淡出，**不留一个孤立的亮点**

并补了单测钉住这个语义：
```
中心与 activeIndex 不同时，activeIndex 不再强制为 1（避免两个亮点）
  out[5] 应为 0（距中心 15 行），实测通过
```

同时验证了"播放行的突出仍由 is-active 负责"：
- 滚动中播放行仍有 `is-active` 类 ✓
- 仍应用 `matrix(...)` scale 放大 ✓
