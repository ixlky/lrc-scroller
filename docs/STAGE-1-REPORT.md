## 二、你该怎么操作（30 秒上手）

### 启动
```bash
cd lrc-scroller
pnpm install     # 首次才需要
pnpm dev         # 浏览器打开 http://localhost:5173/
```

### 导入歌词（两种方式，任选）
- **方式一**：点顶部蓝色的 **「导入 LRC」** 按钮 → 选择文件。
- **方式二**：把 `.lrc` 文件**直接拖到歌词舞台上**，会出现蓝色提示框，松手即可。

导入后**左上角会出现「歌词信息」面板**，点一下展开，里面有：
- 解析提示（重复时间、编码回退、无时间标签等）
- **整体偏移 (offset)** 调节框，可输入毫秒或按 `±100` 微调，改完**立刻**能看到下方时间预览变化
- 文件诊断（探测到的编码、判定依据、原始行数）

### 7 份样例文件在 `samples/` 目录，建议按顺序试

| 文件 | 用来看什么 | 预期现象 |
|---|---|---|
| `01-基础.lrc` | 最普通的歌词 | 11 行，其中 1 行间奏空行 |
| `02-多标签与乱序.lrc` | 多标签 + 乱序 + 重复 | 9 行；顶栏顺序为 0→5→12→12→20→…；出现**重复时间**提示 |
| `03-offset偏移.lrc` | offset 效果 | 顶栏显示 `offset +500ms`；第 1 行显示 `00:00.00` 而原始时间是 `00:00.50` |
| `04-边界情况.lrc` | 各种时间格式与非法值 | 11 行；非法秒数行被忽略 |
| `05-无时间标签.txt` | 没时间标签的纯文本 | **不崩溃**；显示空状态 + "没有找到任何时间标签"提示，并列出 11 行被跳过的文本 |
| `06-只有元数据无歌词.lrc` | 只有 `[ti:]`/`[ar:]` | 不崩溃；提示"这个歌词文件是空的" |
| `07-GBK编码.lrc` | **真正的 GBK 编码** | 中文完全正常；toast 提示"已按 GBK 编码读取歌词"；面板显示探测到 `GB18030` |

### 最值得亲手验证的一件事（offset 无累积误差）
1. 导入 `03-offset偏移.lrc`，展开「歌词信息」
2. 记下预览区第一行的时间（应为 `00:00.00`，原始 `00:00.50`）
3. 把 offset 依次改成 `-300`、再改回 `500`
4. 结果与第一次**完全一致** —— 因为每次都是从 `rawT` 重算，不是叠加

## 五、我参考了 GitHub 上的现成实现（按你的建议）

**先测连通性：GitHub 直连正常**（api 1002ms / raw 378ms / github.com 385ms），**全程未开代理**，你的代理保持关闭、没走流量。

搜到的相关仓库与评估结论：

| 仓库 | 星 | 结论 |
|---|---|---|
| `frank-deng/js-lyrics` | 49 | 参考了它的 offset 约定，但用 ES5 + 单文件写法，无 rawT、无编码处理 |
| `lyswhut/lrc-file-parser` | — | npm 上最活跃、MIT、零依赖，但**源码是 TypeScript**，与你的约束冲突 |
| `yucho123987/lrc-parser` | 0 | **对用户数据抛 `TypeError`**，且只认 3 位小数时间；另有 `padStart(3, 0)` 的 bug |
| `lusaisai/Lyricer` | 31 | 单文件展示库，无解析器源码可复用 |

**决定：保留自研解析器。** 理由不是"想自己写"，而是这些库都不满足你的硬需求：
- 没有一家处理 **GBK 编码兜底**（这是中文歌词最常见的坑，且属于浏览器 IO 层）
- **没有一家暴露 `rawT`**，而你的"offset 重算无累积误差"要求正依赖它
- 最活跃的那个是 TypeScript，用它的编译产物意味着以后无法改

**但从它们身上确实拿到了两个收获：**

1. **交叉验证了 offset 符号约定**。`js-lyrics` 的代码是拿 `currentTime + offset/1000` 去比较行时间的，其 README 写明 *"positive value to shift time up"*。数学上与我的 `t = rawT - offset/1000` **完全等价**。所以我的实现符合事实标准，不是猜的。

2. **发现了"同时间多行"的真实语义**。受 `lrc-file-parser` 与 `lyrics-scrolling` 等库的启示，我意识到同时间多行在中文 LRC 里通常是**原文+翻译**而非错误，于是加了双语识别（即上面额外的那项）。

## 六、过程中发现并修掉的问题（都是实测暴露的）

1. **`useLrcImport` 状态不共享（真 bug，差点漏掉）**
   `useLrcImport()` 被 TopBar / StageView / LyricsInfoPanel 各调用一次，每次都会新建独立的 `lastImport` ref。结果是：导入写进了 TopBar 的那份，信息面板读自己那份永远是空的 → **"文件诊断"区永远不显示**。
   由 e2e 用例 7 抓出。已改为存在 store 里（也符合我定的"store 持有数据、composable 只做副作用"分层规则），并在代码里写明原因防止回退。

2. **双语误判（真缺陷，由样例自检抓出）**
   早期实现只要"同时间各行文本不同"就当作双语，导致两条**不同的纯中文**行挤在同一时间时被静默当成翻译，用户永远看不到"时间重复"提醒。
   已改为按**书写系统特征**判定：日文含假名 vs 中文纯汉字 → 双语；纯汉字 vs 纯汉字 → 报重复。并补了 5 个回归测试。

3. **我自己的测试有 3 处写错**（均已修正，保留说明）：
   - 断言"重复"警告却去读信息面板，而编码提示是走 **toast** 的，读错了地方
   - 只读 toast 的 `.toast__message`，而拒绝音频的说明写在 `hint` 里，漏了内容
   - 没在用例间清理 toast，导致上一条用例的消息串味造成误判
   - 样例 `01` 我手数成 12 行，实际 11 行（顺便把样例里写给用户看的"10 行"文案也改对了）

4. **`**粗体**` 字面显示**：信息面板里 `从文件的**原始时间**重新计算` 在 HTML 里不会渲染成粗体，是我写文案时误用了 Markdown 语法。截图时肉眼发现，已改为 `<strong>`。
