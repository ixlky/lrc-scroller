## 1.2 关键实现决策

**明度条用 HSV 的 V，不用 HSL 的 L。**
iro.js 风格的明度条顶端是**纯色**（V=100）、底端是**纯黑**（V=0）。
若用 HSL 的 Lightness，中段会出现"颜色变白"的效果，与"从纯色渐变到黑"的视觉预期不符。
为此在 `core/color.js` 新增 `rgbToHsv` / `hsvToRgb` / `hslToHsv` / `hsvToHsl` / `valueGradient`。

**感知插值 = smoothstep**，通过 11 段渐变 stops 重排近似实现连续曲线（视觉上与连续无差别）。
拖动点在条上的位置用 **`inverseSmoothstep`（二分求解，24 次迭代）** 反算，
保证"拖动手感与插值模式一致"—— 感知模式下拖到中段，颜色确实在中间亮度。

**色相记忆**：用户把颜色调成纯黑/白/灰时 RGB 里没有色相信息（`rgbToHsl` 返回 h=0）。
若每次都从 `modelValue` 反推，"拉黑再拉回"会让色相莫名跳回红色。
因此沿用原有的 `localHsl` 局部记忆机制，操作由用户直接驱动、不反向覆盖。

# 第二部分：暂停下慢速拖动，歌词不跟随

## 2.1 复现确认（按你的要求：先复现，再定位）

**严格复现需要"每步 <1 秒"**。我的第一次复现用了每步 5 秒的拖速 —— **全部正常**（每步都超过 1 秒阈值）。把拖速改成**每步 0.75 秒**后，bug 精确复现：

```
30 步极慢速拖动（时间从 7s 走到 36s，应跨 ~29 行）
→ activeIndex 只变化 8 次
→ offset 停在 80/158/237/315/393/472 上各连续 3-4 步不动
→ 正是"歌词呆在原地"
```

## 2.2 根因定位（正是你怀疑的那一处）

`useAutoScroll.js` 里：

```js
let lastTime = currentTime.value
watch(currentTime, (t) => {
  const jump = Math.abs(t - lastTime)
  lastTime = t
  if (jump > 1) {              // ← 就是这个阈值
    if (!userScrolling.value) snapToTarget()
  }
})
```

**你的推断完全正确**，机制链条：

1. 暂停时 rAF 循环已停（`stopLoop()`），**没有每帧的平滑跟随**
2. 滚动的唯一通路就是这个"跳变 >1 秒 → snapToTarget"
3. 慢速拖动每步 <1 秒 → **永远达不到阈值** → 不 snap → 歌词原地
4. 播放时 rAF 在跑，`tick()` 每帧平滑跟随，即使不 snap 也能追上 → 正常
5. 快速拖动每步远超 1 秒 → 触发 snap → 正常

**四个现象全部吻合。**

## 2.3 修复（一处，按播放状态分路）

```js
if (!player.playing) {
  // 暂停中：rAF 已停，这里是指滚动的唯一通路
  if (!userScrolling.value) snapToTarget()
  return
}
// 播放中：只有明显跳变（seek）才立即对齐，正常推进交给 rAF
if (jump > 1) {
  if (!userScrolling.value) snapToTarget()
}
```

**性能无虞**：`snapToTarget` → `measureIfNeeded()` 只在 `measured=false` 时才真正测量，拖动中已量好，开销可忽略。
