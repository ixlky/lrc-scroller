## 二、一个重要的方案修正（实测推翻了初稿的假设）

**初稿计划做虚拟滚动，实测证明不需要，因此没有实现。**

初稿的担心是：2000 行会产生约 15 万像素的轨道高度，超出 GPU 纹理上限（常见 16384px）而掉帧。所以我先写好了 `computeVisibleRange` 等虚拟化工具并配了测试。

**但实测数据否定了这个判断：**

| 行数 | 轨道高度 | 平均帧率 | 最差帧 | 堆内存 |
|---|---|---|---|---|
| 2000 | 157,294px | **60fps** | 16.8ms | 25–32MB |
| 5000 | 648,167px | **60fps** | 16.8ms | 40MB |
| 10000 | 1,360,042px | **60fps** | 16.8ms | 65–72MB |

浏览器对超长合成层的处理比预期好得多。因此我**删除了已写好的虚拟化代码**，改为全量渲染 + `transform` 单层合成：

- 少一层复杂度，就少一类隐患（窗口计算错位导致的空白/跳行）
- 已实测 10000 行仍 60fps，余量充足

这个决定已记入 [PLAN.md](lrc-scroller/docs/PLAN.md)（含推翻理由与数据），若将来在低端机上真的遇到掉帧，可按记录重新引入。

另外正确去掉了一个**会严重掉帧的写法**：`will-change: transform` 只写在轨道层，**没有**写在每一行上 —— 若 2000 行各自声明，浏览器会尝试建立上千个合成层。

## 三、发现并修掉的问题

### 1. 真 bug：色相环拖动完全无反应（由控制台错误定位抓出）
`setPointerCapture` 在没有"活动指针"时会抛 `NotFoundError`。我原来把它写在处理函数**第一行**，异常直接中断整个函数 —— 表现为**拖动色相环毫无反应**，且不报给用户。
修复：先响应、再尽力捕获指针（`try/catch` 包裹），捕获失败不影响主流程。

### 2. 同类隐患：播放条拖动也有同样问题
`PlayerBar` 的 `attachDrag` 有完全相同的写法 —— 抛异常发生在 `onMove` 之前，会导致"拖进度条没反应"。已一并修复。
> 这类 bug 靠肉眼点几下很难发现（有时能拖、有时不能），是靠"捕获完整异常描述"才定位到的。

### 3. 真 bug：首行永远无法居中（偏差达 92px）
我最初把位移夹取成 `[0, 内容高 - 容器高]`（按页滚动的语义）。但"让首行居中"所需的位移**本来就是负的**（要把轨道往下推），被这个下界压成 0，于是第一句永远贴在顶部而不是中间。
修复：改用**居中几何语义**算区间 —— 下界 = 首行居中位移，上界 = 末行居中位移。同时补上上下留白占位块（用像素高度，因为百分比在 auto 高度的父元素上无法解析）。
修复后 14 行逐行偏差 ≤0.56px。

### 4. 真 bug：滚轮滚动被整次丢弃
原写法是"如果这次滚动会越过边界，就整体 `return` 不处理"。后果：还剩 314px 可回看空间时，一次 -400px 的滚动被**完全丢弃**，用户感觉"滚了没反应"。
修复：只要没贴到边界就接管并**夹取**到边界；只有贴着边界继续往外滚时才交还页面。

### 5. 调试钩子因模块加载时序而失效
`main.js` 里 diagHooks 是动态 `import`，而 `app.mount()` 是同步的 —— StageView 的 setup 先执行，此时 `window.__lrcDiag` 还不存在，注册被静默丢弃（表现为 `auto` 永远是 `null`）。
修复：加入 `_pendingAuto` 暂存，挂载完成后补上。

### 6. 我的测试有 5 处写错（均已修正，保留说明）
- **颜色测试选了无效的变化**：默认色是纯白 `#ffffff`，把 R 通道拖到 255 属于"原地不动"，测不出变化。已改为取非极值再拖（白 → 青）。
- **断言了错误的前提**：我原本断言"必须启用虚拟滚动（DOM 行数 < 200）"，但实测证明不需要虚拟化。已改为断言真正的性能目标（帧率、长任务），并记录 DOM 规模作为参考。
- **放大测试在首行进行**：首行没有"上一行"，核心断言恒为 `null`。已改为跳到第 6 行。
- **未隔离 localStorage**：设置持久化生效后，上次运行残留的 `44px` 让"初始应为 40px"失败。已在各套件开头清一次（**只清一次**，不用 `addScriptToEvaluateOnNewDocument`，否则会破坏"刷新后恢复"用例）。
- **回看测试在歌曲开头进行**：开头时位移已在下界，向上滚会被边界逻辑正确拦下（设计如此），不会进入回看状态。已改为跳到中部。

### 7. 阶段 0/2 的过时断言（不是回归）
移除调试胶囊、以及颜色控件换成调色盘后：
- stage 0 的"C. 预览按钮切换当前行"与"改颜色"两处引用了已不存在的元素 → 改为通过 seek 验证二分查找联动、通过 store 验证颜色链路

## 四、这一阶段的技术要点

| 要点 | 做法 | 原因 |
|---|---|---|
| 滚动 | 容器 `overflow:hidden` + 轨道 `translate3d` | `scrollTop` 会触发主线程布局重绘；transform 走 GPU 且不参与布局 |
| 放大 | `transform: scale()` | 不改变行高，所以相邻行纹丝不动（验收项 2） |
| 每帧成本 | 只写 1 次 transform，**从不读布局** | 避免 layout thrashing；行几何只在歌词/排版变化时测量并缓存 |
| 平滑 | 帧率无关的指数平滑（半衰期 90ms） | 常见写法 `v += (t-v)*0.15` 在 120Hz 屏上会快一倍，手感不一致 |
| 用户滚动 | 状态机 + 3 秒静默恢复 | 播放继续但**绝不强拉回**（验收项 3） |
| 持久化 | 300ms 防抖写入 + 逐字段兜底 | 拖滑杆每帧都写会卡；隐私模式/配额满时降级并提示 |
| 颜色 | 独立 `core/color.js`（纯函数） | HSL 往返在灰阶/黑白色容易丢色相，需单测覆盖（已用 1.2 万组取样验证） |
