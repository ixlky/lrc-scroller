## 一、问题 1：拖动进度条回滚到 0:00

### 1.1 先复现（用真实输入，而不是合成事件）

**这里有个重要发现：我之前的拖动测试用的是 `new PointerEvent()` + `dispatchEvent()` 合成事件，它没有真实的活动指针，所以 `setPointerCapture` 那条路径压根没被测到。** 这次改用 CDP `Input.dispatchMouseEvent` / `dispatchTouchEvent` 发真实输入。

但真实鼠标/触摸拖动**都通过**了（连拖 5 次、50→20→80 全部正确）。所以问题另有条件。于是我在引擎调用链上打了桩，记录每次 `scrubTo` / `endScrub` 的**入参**，最终抓到三条路径：

```
拖到 60%:  scrubTo(36)          →  endScrub(0)      ← pointercancel 的 clientX=0
拖到 70%:  scrubTo(42)          →  endScrub(0)      ← 同上
拖到 30%:  scrubTo(30)          →  endScrub(NaN)    ← NaN 直接进了 endScrub
```

**调用序列直接指出了故障点**：最后一步 `endScrub` 收到的不是用户落点，而是 `0` 或 `NaN`。

### 1.2 定位到的根因（**你怀疑的两条都命中了**）

**根因 A：`pointercancel` 没有有效坐标，却被当成落点**（这是"第二次拖动回 0"的真凶）

`attachDrag` 里 `pointerup` 与 `pointercancel` 共用同一个结束处理，都用事件坐标算落点：

```js
const up = (ev) => { ...; onEnd?.(ratioOf(ev)) }   // ← pointercancel 也走这里
el.addEventListener('pointerup', up)
el.addEventListener('pointercancel', up)
```

而 `pointercancel` **不携带有效坐标**（实测 `clientX = 0`，因为它是"指针被系统/滚动接管"的通知，不是用户选点）。于是算出 ratio = 0 → `endScrub(0)` → **时间跳回 0:00**。

**为什么表现为"第二次"**：真实场景中第一次拖动常以 `pointercancel` 结束（触控板手势、页面滚动接管、长按菜单等），它把位置写成 0，第二次就从 0 开始了。

**根因 B：NaN 被静默转成 0**（正如你指出的）

```js
const target = Math.max(0, Math.min(Number(time) || 0, max))   // NaN || 0 → 0
```

`Number(undefined) || 0` 得到 0，`Math.max(0, ...)` 再兜一层，**没有任何 `Number.isFinite` 拦截**，NaN 一路传到 `seek` 并落到 0。

### 1.3 修复内容

**① 区分"选定落点"与"取消"**（`PlayerBar.vue`）
- `pointerup` → 用事件坐标确定落点
- `pointercancel` → **沿用当前位置**，绝不当成 0
- 但**必须仍然收尾**（见下方"修复过程中自己引入的一个 bug"）

**② 坐标换算加三重防御**（`ratioOf`）
```js
const x = ev?.clientX
if (!Number.isFinite(x)) return null          // ① 非有限值 → 返回 null，不返回 0
const rect = el.getBoundingClientRect()
if (!(rect.width > 0)) return null            // ② 元素未布局
const raw = (x - rect.left) / rect.width
if (!Number.isFinite(raw)) return null        // ③ 结果校验
return Math.min(1, Math.max(0, raw))
```
**关键：非法值返回 `null` 表示"未知"，而不是返回 0。** 0 是一个合法的用户落点（拖到最左端），两者语义完全不同，混用就是 bug 的源头。

**③ 引擎入口强制校验**（`useAudioEngine.js`）
`seek()` / `scrubTo()` / `endScrub()` 全部加 `Number.isFinite` 拦截：
- 非有限值**拒绝执行**并返回 `false`，不再被 `Math.max(0, ...)` 静默夹成 0
- `endScrub(undefined)` 表示"坐标不可用" → 把当前位置固化，不做跳转

**④ 监听器从元素移到 `window`**
原来挂在元素上：一旦指针拖出元素外，`pointerup` 就不再落在该元素，导致 `up` 永不执行 → `scrubbing` 卡在 `true`、监听器残留到下一次拖动。挂到 `window` 后必然收到收尾事件。

**⑤ 每次 `beginScrub` 重置 seek 保护**
实测发现拖动结束后 `guardActive` 一直是 `true`。若上一次因异常没正常收尾，`guard` 会残留陈旧目标值，影响下一次拖动的起点显示。

### 1.4 修复过程中我自己引入的一个 bug（已修，记录下来）

第一版修复里我把 `pointercancel` 写成"直接 return，不做任何处理"。结果 **`scrubbing` 永远停在 `true`** —— 而 tick 在 `scrubbing` 期间不写 `currentTime`，表现为**进度条永久卡死**。
测试用例 E 立刻抓到了（`pointercancel 后 scrubbing 已复位 → scrubbing=true`）。
教训：**"不改落点"与"不结束拖动"是两件事**，不能混为一谈。正确的做法是仍然收尾，只是用 `undefined` 表示"坐标不可用"。

## 二、问题 2：歌词虚化

### 2.1 实现要点

新增 `src/core/fade.js`（纯函数层，可 Node 单测）：

| 概念 | 实现 |
|---|---|
| **逻辑行** | 把"时间相同"的连续物理行归为一组。这是**双语算一行**的基础 —— 否则译文会白占一格，导致上下距离不对称 |
| **实体区** | `\|距离\| ≤ 实体行数` → opacity = **1** |
| **过渡区** | `实体 < \|距离\| ≤ 实体+过渡` → 从 1 渐变到 0 |
| **超出范围** | opacity = **0**（完全不可见） |
| **模式** | `linear` 匀速 / `ease` smoothstep（两端平缓）/ `none` 实体区外直接隐藏 |
| **缓存** | `createFadeEngine()` 显式记账计算次数，可被验收脚本证明"没有逐帧重算" |

### 2.2 一个我必须纠正的地方（重要）

第一版我把虚化值与阶段 3 的 `past(0.38)` / `upcoming(0.55)` 明暗基准**相乘**了。结果实体区实测显示为 **0.38**，而不是 1。

但你的需求原文是：
> 实体区：当前行上下各 N 行保持**完全不透明**
> 过渡区：透明度**从 1 渐变到 0**

**"完全不透明"就是 1**，叠加明暗基准与这条要求直接冲突。所以我改成：**虚化开启时透明度完全由距离决定**（实体区真的 = 1），虚化关闭时才回落到阶段 3 的按行明暗区分。

修正后的实测透明度剖面（ease，实体上下各 2，过渡 7）：

```
  d= -9  0.055  ##
  d= -8  0.198  ######
  d= -7  0.394  ############
  d= -6  0.606  ##################
  d= -5  0.802  ########################       第 9 行（双语·原文）
  d= -4  0.802  ########################       Line 9（双语·译文）  ← 与上一行完全相同
  d= -3  0.945  ############################
  d= -2  1      ##############################  ← 实体区
  d= -1  1      ##############################
  d=  0  1      ##############################  当前行
  d=  1  1      ##############################
  d=  2  1      ##############################  ← 实体区
  d=  3  0.945  ############################
  ...
  d=  8  0.055  ##
  d=  9  0       （完全不可见）
```

这张表同时验证了三件事：**实体区 = 1**、**过渡区单调 1→0**、**双语两行透明度完全相同**。

### 2.3 一个需要你知道的语义细节

过渡区是跨度 `fadeRows` 的斜坡，在 `over = fadeRows` 处**恰好降到 0**。所以：
- `过渡行数 = 5` → 第 1~4 行部分可见，**第 5 行正好不可见**
- 想"5 行都还看得见" → 把过渡行数设为 **6**

我选择这个定义是因为：斜坡宽度就等于你设置的数值，且到边界恰好归零、不会留一条"半透明幽灵行"。这条已写进 PLAN 和代码注释。

## 三、我的测试有 2 处写错（已修正，保留说明）

1. **误以为"对象读取失败 = 代码有 bug"**：`returnByValue: true` **无法序列化 Vue 的响应式 Proxy**，会返回 `{}`。我一看到"刷新后 fade 是空对象"就怀疑 setup 有问题，实际数据完好（`JSON.stringify` 读出来是对的）。已新增 `evalJson()` 辅助方法绕开，并在代码注释里记下这个坑。
2. **用 `getComputedStyle` 判断"是否滞后"**：`.lyric-line` 上有 `transition: opacity`，跳转后立刻取计算样式拿到的是**过渡中间值**（例如 0.12），看起来像滞后，其实是动画进行中。已改为读 `data-opacity`（组件按最终目标值渲染的属性），并额外断言"过渡结束后实际值确实为 1"。

另外一处判断错误：我原以为"双语两行应同时为 active"，实际 `findLineIndexAt` 返回**最后一个** `t <= currentTime` 的行，所以同时间的双语对只有后一行是 active（这是阶段 3 的既定行为，保证"当前正在唱的那句"唯一）。已改为断言正确的不变量。
