# 第一部分：纯黑 / 纯白下拖色相环，颜色显不出来

## 1.1 先复现（数值证明，不是猜）

```
#ffffff  HSL(0,0%,100%)   h=90→#ffffff  h=210→#ffffff  h=330→#ffffff   不变✗
#000000  HSL(0,0%,0%)     h=90→#000000  h=210→#000000  h=330→#000000   不变✗
#808080  HSL(0,0%,50%)    h=90→#80936c  h=210→#6c7f93  h=330→#936c80   变色✓

hslToRgb(210, 15%, 100%) = #ffffff   ← 饱和度被亮度吞掉
hslToRgb(210, 15%,   0%) = #000000
```

**你的分析完全正确。** 纯白在 HSL 里是 `h=0, s=0%, l=100%`，把 s 提到 15 仍然是纯白。

**但我还发现了你没提到的范围**：接近白/接近黑时同样有问题，只是没退化到"完全不变"：

```
#f0f0f0 (L=94%)  h=210 → #f2edf0     ← 技术上"变了"，视觉上完全看不出
#0f0f0f (L=6%)   h=210 → #0d0f12     ← 同理
```

所以修复不能只针对 `#ffffff` / `#000000` 两个端点。

## 1.2 根因：判据用错了 —— 该看绝对色度，不是饱和度

HSL 里饱和度的定义是 `S = (max-min)/(1-|2L-1|)`，反解出通道差（绝对色度）：

```
chroma = S × (1 - |2L - 1|)
```

那个因子在 **L=0% 和 L=100% 时等于 0** —— 亮度拉满或归零时，饱和度被**完全吞掉**，所以提 S 一点用都没有。

| 起始色 | L | 提 S 到 15 后 | chroma | 结果 |
|---|---|---|---|---|
| 中性灰 `#808080` | 50% | `15 × 1` | 15 | 显色 ✓ |
| 纯白 `#ffffff` | 100% | `15 × 0` | **0** | 不变 ✗ |
| 近白 `#f0f0f0` | 94% | `15 × 0.12` | 1.8 | 几乎看不出 ✗ |
| 纯黑 `#000000` | 0% | `15 × 0` | **0** | 不变 ✗ |

## 1.3 修复

核心函数 `core/color.js` 的 `ensureHueVisible(hsl)`，三步：

1. **已是彩色 → 完全不动**（保持用户的饱和度与亮度，这条优先级最高）
2. 把 S 提到 `MIN_VISIBLE_SATURATION = 15`
3. chroma 仍不足 → 把 L 拉进可见区间 `[20, 80]`，**逐 1% 逼近**到刚达标

```js
// core/color.js
export function ensureHueVisible(hsl) {
  const h = ...
  const s0 = ..., l0 = ...
  if (isHueVisible(s0, l0)) return { h, s: s0, l: l0 }   // 彩色：原样返回
  let s = Math.max(s0, MIN_VISIBLE_SATURATION)
  let l = l0
  if (isHueVisible(s, l)) return { h, s, l }
  const target = l > VISIBLE_L_MAX ? VISIBLE_L_MAX : VISIBLE_L_MIN
  const step = l > target ? -1 : 1
  while (!isHueVisible(s, l) && l !== target) l += step
  return { h, s, l }
}
```

### 阈值不是随手定的：它由 L 的边界精确导出

```
亮度被拉到 L=80 时，亮度因子 (1-|2L-1|) = 0.4
0.4 × 15（最小饱和度） = 6
```

于是 **"把 L 拉到 80/20" 与 "色度达标" 这两件事恰好同时成立**。这带来两个好处：

- 亮度只做**最小必要**的调整（不会被一路拉到 50% 那种过头值）
- 饱和度**保持 15% 不被拉满** —— 你看到的是淡雅的一层色相，不是浓艳的颜色
- 代码里"色度仍不达标就拉满饱和度"的兜底分支因此**数学上不可达**（单测里穷举验证）

**L 上下限为什么不是 50%**：直接拉到 50 会让"我想要一个很亮的颜色、只是微调一下色相"的用户突然得到中等亮度的彩色，跳变太粗暴。80/20 既能显色，又保留了用户的明暗意图。

## 1.5 我踩的一个真实浮点坑（已固化进单测）

第一版我把阈值写成 `Math.round(15 × 0.4) = 6`，结果**纯白被拉成浓艳的 `#ccff99`（S 被拉满到 100）**。

```
hslChroma(15, 80)  = 5.999999999999998   ← 浮点下溢，比 6 略小
阈值 6
5.999999999999998 >= 6  →  false          ← 边界点被误判为"不可见"
```

于是 L 继续被下拉 → 触到兜底把 S 拉满。

我第一次的修法方向还搞反了（写成 `+1e-9` 上调 → 6.000000000999998 仍然大于 5.9999...，依然误判），**正确方向是下调** `6 - 1e-9`。现在单测里有专门一条断言把这个钉死：

```js
assert.ok(MIN_VISIBLE_CHROMA < 6, '阈值必须略小于 6（下调 epsilon），否则浮点边界会误判')
assert.ok(MIN_VISIBLE_CHROMA > 5.999999, 'epsilon 不应大到改变判定语义')
```

# 第二部分：阶段 4 · 展示 / 全屏模式

## 2.1 三个设计决策（已与你确认）

| 决策 | 选择 |
|---|---|
| 进全屏时控制条第一次出现 | **就隐藏**（干净歌词，鼠标一动才淡入） |
| 全屏里的控制条 | **复用现有 PlayerBar 全功能** |
| 退出路径 | **两条路都走**（自己的 Esc/按钮 + 监听原生 `fullscreenchange`） |

## 2.2 架构：三层，每层都可以独立失败

```
① 模式状态   isPresenting        纯状态，UI 是否隐藏
② 浏览器全屏 requestFullscreen   只是让浏览器进全屏 —— 受限环境拿不到
③ 空闲隐藏   鼠标动 → 淡入，静止 2s → 淡出
```

**关键决策：全屏不能是进入展示模式的前提。** iOS Safari 不支持任意元素全屏（iPhone 上 API 根本不存在，iPad 上直接抛错）。如果做成"必须拿到全屏才能进演示"，iOS 用户就完全用不了。所以全屏只是锦上添花，拿不到就降级为 `fixed + 100dvh` 的伪全屏，**功能完全一致**，并弹一条提示。

## 2.3 三个真实 bug（都写进了 CSS 注释）

### ① 控制条永远淡不回来

第一版把 `.playerbar` 放进了"展示模式无条件隐藏"那一组：

```css
.app-shell.is-presenting .topbar,
.app-shell.is-presenting .playerbar,   /* ← 问题在这 */
... { visibility: hidden; }
```

然后"空闲"规则只写了 `transition`：

```css
.app-shell.is-presenting:not(.is-control-hidden) .playerbar {
  transition: ...;   /* ← 只能改 transition，改不回 visibility */
}
```

结果 `controlVisible` 明明是 true（诊断里 idle 倒计时在跑），但 CSS 仍是 hidden。

**教训写进注释了**：CSS 是层叠覆盖，不是状态机。两套状态（隐藏/显示）必须**完整**写出 `opacity` / `visibility` / `pointer-events` / `transition` 四项，漏写哪一项就沿用上一条的值。

### ② 控制条淡回来了但只有 1px 高

修好①之后，"全屏中拖进度条"仍然打不中。原因是布局：

```css
.app-shell.is-presenting { grid-template-rows: 0 minmax(0,1fr) 0; }
```

播放条的行高确实是 0，被 `overflow:hidden` 夹成了看不见的一条。**CSS 层叠只管"显不显示"，不管"有没有地方给你显示"。**

改成：播放条在展示模式下 `position: absolute` **浮在舞台底部**，脱离网格流。行列全归零，舞台真正占满，播放条自己决定高度。

顺带发现 `.app-shell` 必须是 `position: relative` —— 原生全屏时 shell 仍是 `static`，absolute 会退回视口定位。

### ③ 截图才发现的两个视觉漏项

自动化测试全绿之后我截了图，看到两个断言查不出的问题：

- **"歌词信息"面板还在左上角**（`.info`）—— 第一版只写了 topbar/toasts/drawer，漏了它。已加入隐藏组。
- **底部一条白边** —— 伪全屏下 `100dvh` 的壳下面露出 body 背景。因为播放条行还留着 68px 却没人画。改成行高全 0。

另外控制条原本用 `var(--ui-panel)` 做半透明毛玻璃，在深色舞台上会变成**刺眼的白带**。改成固定的深色半透明 + 模糊，让它隐入舞台。

## 2.4 其他实现细节

- **单例**：`useFullscreenShared()` —— App.vue / TopBar / useKeyboard 三处共用同一份状态，否则按钮和按键会各说各话，事件监听也会注册三次。
- **抖动阈值**：指针移动 <6px 忽略，否则鼠标轻微晃动会让控制条永远不淡出。
- **F 键输入保护**：在 HEX 输入框里打 `ffffff` 时按 F 是在**输入 f**，不能切全屏。已在 `isTypingTarget` 基础上覆盖。
- **Esc 不越权**：只在展示模式下拦截 Esc，正常界面里 Esc 还给浏览器（关抽屉、退出原生全屏）。
- **监听原生 `fullscreenchange`**：用户用 F11 / 系统手势退出时跟着退出，否则界面卡在"全没了"（已登记为 N16）。
- **减少动态效果**：`reduce-motion` 下所有过渡为 `none`。

# 附：补丁 7 — 原生全屏下开过设置后右侧出现白边

> 真机报告的 bug。已修复，e2e-stage4 从 69 → **86 项**（新增 15 项白边回归 + 2 项归位）。

## 3.1 你的假设可以排除（实测否定，不是推理）

**"打开抽屉时给 body 加的滚动锁补偿没还原干净"** —— 项目里**根本不存在任何滚动锁代码**：

```
搜索 documentElement.style / body.style / setProperty / .style. 写入
→ 全项目仅 1 处：useAutoScroll.js:201  track.style.transform
→ 实测 bodyStyle / htmlStyle 全程 = "(无)"
```

`padding-right` 本身也还原得干干净净（实测三态）：

```
从未开抽屉  padRight=0px    stageW=1400
打开抽屉    padRight=360px  stageW=1040
关闭抽屉    padRight=0px    stageW=1400   ← 类与 CSS 都正常
```

## 3.2 真正的根因

关键在 `supportsElementFullscreen` 为真时走原生分支，而**原生全屏时 `.app-shell` 就是全屏元素**：

```css
.app-shell.is-presenting {
  grid-template-rows: 0 minmax(0, 1fr) 0;
  /* ← 缺 padding-right: 0 */
}
```

`.app-shell.is-drawer-open`（特异度 0,2,0）同特异度下被后面的规则覆盖，但**展示模式这条根本没写 `padding-right`**，所以只要 `is-drawer-open` 还在，那 360px 就继续生效。

**为什么会露出白色**（这是最关键的一环）：`.app-shell` 自身背景是**透明**的 —— 实测 `background: rgba(0,0,0,0)`，深色舞台只由 `.app-stage` 的 `var(--lrc-bg)` 绘制。原生全屏时浏览器把全屏视口底色交给元素自己画，`body` 已不在这个渲染上下文里，于是右侧那 360px 没有任何背景 → **露出的就是浏览器白色画布**。

实测证据：

```
全屏中开抽屉: is-drawer-open is-presenting   padRight=360px  stageW=1040
全屏中关抽屉: is-presenting                   padRight=0px    stageW=1400
```

**触发条件是「抽屉开着时进演示」**（`is-drawer-open` 与 `is-presenting` 共存），而不是"关过抽屉"这一动作本身 —— 关抽屉时类会被移除，状态是干净的。你复现步骤里的第 2 步 Esc 退出后第 3~4 步只开关抽屉、此时还没进全屏，所以那 360px 已经归零；真正的触发点应该是**抽屉还开着时**按 F / 点演示。

## 3.3 修复（两层防御）

**第一层 · CSS 兜底**（管"无论怎么进来都不出错"）：

```css
.app-shell.is-presenting {
  grid-template-rows: 0 minmax(0, 1fr) 0;
  padding-right: 0;          /* ← 展示模式里抽屉是隐藏的，避让毫无意义 */
  background: var(--lrc-bg); /* ← 全屏元素自己画底色 */
}
```

第二条同样重要：全屏元素必须自己刷底色，否则**未来任何一处"没被画到"的地方都会露白**。用 `var(--lrc-bg)` 而非写死黑色，用户在设置里改的歌词背景色也能顺带覆盖到全屏边缘。

**第二层 · 源头不共存**（管"状态本身就不该出现"）：

`enterPresentation` 增加 `onBeforeEnter` 钩子，在进展示模式前关掉抽屉，两个入口都接上：

- `TopBar.vue` 的「演示」按钮
- `useKeyboard.js` 的 F 键

```js
full.toggle(shell, { onBeforeEnter: () => settings.closeDrawer() })
```

> 顺带修掉一个**说谎的注释**：`enterPresentation` 里原本写着「先关掉设置抽屉」，但代码从来没做这件事 —— 是一句写于草稿期、从未兑现的注释。

## 3.4 为什么之前没测到

`e2e-stage4` 里所有涉及 padding 的断言都在 **"抽屉关闭"状态下**执行，因此 `is-drawer-open` 与 `is-presenting` 从未共存，bug 自然测不出来。更根本的是：**白边只在原生全屏下可见**，而 headless 里 `requestFullscreen` 返回**永不 settle 的 Promise**，`enterPresentation` 会卡在 `await` 上 —— 所以整个测试套件从头到尾都跑在伪全屏路径上（这也顺带成了"全屏不作为进入前提"这个设计的免费验证）。

新增的 15 项回归覆盖 4 个场景：

| 场景 | 内容 |
|---|---|
| A | **抽屉开着 + 直接进展示模式**（真正的触发条件）→ 断言抽屉已自动关闭、padding=0、舞台铺满、全屏元素自己画了底色 |
| B | **CSS 兜底**：手动强制 `is-drawer-open` + `is-presenting` 共存，验证 padding 仍为 0（不依赖 JS 兜底） |
| C | **用户给的复现步骤**：开→关→再进全屏，断言无残留 |
| D | **不回归**：退出全屏后抽屉避让量正常恢复、关闭后完全还原 |

## 3.5 顺带修掉的一个测试陷阱（花了不少功夫才定位）

排查中发现我的降级测试一直无效，症状很奇怪：`isDegraded: true` 但 `degradedReason: null`、`toasts: 0`。

用探针测出真相：**`supportsElementFullscreen` 被调用次数为 0 次**。

```js
full.supportsElementFullscreen = () => false   // ❌ 无效
```

那是 return 对象上的一个**副本**，而 `enterPresentation` 内部调用的是**模块作用域里的闭包** —— 改副本对它完全无效。代码仍走原生分支 → `requestFullscreen` → headless 下永不 settle 的 Promise → 函数永久卡在 `await` 上，else 分支（降级提示）永不执行。

**正确做法是让能力探测本身认为不支持**，从根上关掉：

