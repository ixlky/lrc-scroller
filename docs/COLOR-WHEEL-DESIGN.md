| 你的理解                                     | 确认                                     |

## 一、色轮内部坐标：**HSV**（与明度条一致，不引入混用）

### 为什么是 HSV 而不是 HSL

|          | HSV 的 V              | HSL 的 L              |
| -------- | -------------------- | -------------------- |
| 与明度条的关系  | **同一个量**，色轮与明度条天然共用  | 不同量，两者会互相打架          |
| 拖动色轮时的表现 | V 不变，只改 H 和 S → 明暗稳定 | L 随 S 变化，拖到边缘颜色会忽明忽暗 |
| 用户心智     | "轮子选颜色，竖条调明暗"，两件事正交  | 两条控件都在改"亮度"，含义重叠     |

现有明度条已经是 HSV 的 V（补丁 5 定的），色轮再用 HSV **不需要任何跨模型转换**。

### 内部状态怎么办：把 `localHsl` 换成 `localHsv`

**这是我唯一要动的状态结构**。现在：

```
localHsl（HSL）──是──▶ localHsv（HSV，明度条用，computed）
```

改成：

```
localHsv（HSV）──是──▶ 一切（色轮、明度条、RGB 滑杆都从它派生）
```

`localHsl` 只在"HEX 输入 / 外部改色"时用来反推一次，算完就丢。**这样拖动路径上不存在 HSL↔HSV 往返**，也就不存在往返误差累积。

### 会不会抖？实测数据

我跑了全网格（360 × 100 × 100）的往返检验：

| 指标                                     | 实测值                    | 结论                                              |
| -------------------------------------- | ---------------------- | ----------------------------------------------- |
| HSL→HSV→HSL 的 **RGB 通道差**（走一圈回来颜色是否一样） | **最大 5 / 255（2%）**     | 发生在 `L=90` 附近（`#feaeae` vs `#ffb3b3`），**肉眼不可辨** |
| 误差分布                                   | L≤60 时 ≤2；L=70~90 时 ≤4 | 集中在高亮度区，因为那里 RGB 接近饱和                           |
| 拖动 1px（S 变 1）的 RGB 变化                  | **1~2 级**              | 远低于可见阈值，**不会抖**                                 |
| 走 HEX 中转（真实链路）                         | 最大 2/255               | 无感                                              |

**注意**：如果保留 `localHsl` 做中间层，每拖 1px 都要往返一次，误差会累积。改成 `localHsv` 后**拖动路径上零往返** —— 这是我在动手前实测才敢这么定的原因。

> 我也顺手核实了一个可疑数字：H 的"往返误差 355°"是 **0/360 环绕**的假象（`h=355` 归一化成 `0` 是合法表示），不是错误。改用环形距离重算后，高饱和区误差 ≤5°。

## 二、拖动小点：**你理解正确，确认如下**

```
小点到中心的直线距离 → S（0~100，中心 0，边缘 100）
该直线的角度         → H（0~360，顶部 0°，顺时针）
```

**中心 12px 死区**：半径小于 12px 时 S 恒为 0。  
理由：小点在中心附近时，1px 位移会让 S 剧烈跳变（`S = 100 × r/R`，r 从 0 到 1px 就是几个百分点），很难精确停在低饱和区。死区让"我要纯灰"这个意图可以直接点中心达成。

**S 的分布用线性还是平方根？** 我倾向**线性**（`S = 100 × r / R`）—— 半径是用户能直接感知的量，线性映射符合直觉；平方根会让边缘一小段挤掉大量 S 值。

## 三、明度条与色轮的联动（你专门问的）

### 明度条拉到最黑，色轮会不会"废掉"？

**会视觉上全黑，但功能完全可用。** 实测：

| V  | 中心（S=0）   | 边缘·绿（S=100） | 边缘色差 |
| -- | --------- | ----------- | ---- |
| 0  | `#000000` | `#000000`   | 0    |
| 6  | `#0f0f0f` | `#000f00`   | 15   |
| 12 | `#1f1f1f` | `#001f00`   | 31   |

V=0 时整轮都是黑的，看不出选了哪个色相 —— **但这是明度条的状态决定的，不是色轮缺陷**。

### 关键：怎么保证"能从黑里拉回来"？

**不靠重新计算，靠"不重算色相"。** 具体做法：

- 拖色轮时，只改 `localHsv.h` 和 `localHsv.s`，**`localHsv.v` 保持不变**（除非用户拖了明度条）
- 所以纯黑状态下点绿色区域，得到的是 `h=120, s=100, v=0` → 仍是黑
- **但小点的位置会立刻跳到那个角度和半径上** —— 用户看到"我选中了绿色"
- 这时拖明度条，V 从 0 升到 100，**颜色一路变成绿色**，全程不丢失色相

这正是 HSV 相对 HSL 的优势：**色相与饱和度独立于明度**，不会因为变黑就被抹掉。（HSL 则不行：L=0 时 H 和 S 都被退化掉了。）

> 补一句：纯白/纯黑下 HSV 同样会丢失色相（`#ffffff → HSV(0,0,100)`）。但因为我们**不从 HEX 反推色相**（下面的设计要点），色相由用户点的位置直接决定，所以不存在丢失问题。

## 四、「重置为白色」：确认按你说的做

**语义 = 重置为纯白 `#ffffff`**，不做"恢复上次保存的颜色"。

理由：纯白是 HSL/HSV 的**最中性起点**（V=100, S=0），点一下就回到"从头调"的干净状态。做成"恢复上次保存"会让人搞不清当前基准是什么。

实现上它就是一次 `commitHex('#ffffff', { h: 0, s: 0, v: 100 })` —— 但**色相记忆要特殊处理**（见下）。

## 五、一个必须解决的设计要点：**色相记忆**

这是我在推演时发现的关键问题，也是补丁 9 那个 bug 的同源。

### 问题

`#ffffff` 反推 HSV 得到 `h=0`（红）。如果色轮小点跟着这个 h=0 走，那么：

- 用户点"重置为白色" → 小点跳到 12 点方向（红区）
- 视觉上像是在说"现在是红色"，但颜色明明是白的

### 解法

**小点的位置只在用户拖动时更新，不由颜色反推。** 具体：

- 引入一个 `hueMemory`（默认 0），只在**用户拖色轮时**写入
- 从 HEX 反推 HSV 时，**用 `hueMemory` 覆盖算出的 h**，只在颜色真的变了色相时才更新记忆
- 这样"重置为白色"后小点仍停在用户上次选的角度，不会莫名跳到红色

这和现在 `localHsl` 保留色相记忆的思路一致（`ColorPicker` 里已有 `localHsl` 在做这件事），我只是把它从 HSL 挪到 HSV。

> **顺带说明**：补丁 9 修的 `selfUpdate` bug 就是这个问题的极端形态 —— 纯白时 emit 的值与原值相同 → watch 不触发 → 标记卡死。色轮方案下"颜色不变"的情况大幅减少（点任何位置都会变色），但纯白/纯黑仍可能发生（比如 V=0 时点色轮颜色不变），所以 `selfUpdate` 的修法要保留。

## 八、技术坑（我识别到的 4 个）

| # | 坑                                                                                               | 处理                                                |
| - | ----------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 1 | **色轮背景的渐变实现**：`conic-gradient` 铺色相 + 白色径向遮罩做 S。如果遮罩用 `rgba(255,255,255,1)` 会把中心变纯白而不是"当前明度下的灰"。 | 遮罩要用**动态的灰度**（按当前 V 生成），否则 V≠100 时中心色不对           |
| 2 | **色轮在 V 很低时几乎全黑**，用户看不出选了什么                                                                     | 小点加白色描边（`box-shadow: 0 0 0 1.5px #fff`）保证任何背景下都可见 |
| 3 | **`selfUpdate` 卡死**（补丁 9 修的那个）在纯白/纯黑下仍会触发                                                       | 保留补丁 9 的修法（用 `selfEmitted` 记值），这是必需的              |
| 4 | **点色轮的坐标 → 色相要处理 0°/360° 环绕**                                                                   | `pointToHue` 已有 `((h%360)+360)%360` 归一化，直接复用      |

**没有明显的技术风险**。最大的工作量反而是 UI 细节（遮罩、描边、响应式尺寸）。
