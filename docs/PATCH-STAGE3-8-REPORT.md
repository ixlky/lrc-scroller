# 一、降级提示被 CSS 吞掉（用户可见 bug + 测试假阳性）

## 1.1 根因

`.toasts` 被我归进了展示模式的「无条件隐藏」组：

```css
.app-shell.is-presenting .toasts { opacity: 0; visibility: hidden; ... }
```

两个后果：

1. **用户看不到提示** —— 伪全屏降级时那条"已切换为伪全屏"被一起吞掉。用户只看到"界面突然全没了"。更糟的是**原生全屏有浏览器自带的「按 Esc 退出」提示，伪全屏没有这层兜底** —— 用户不知道能按 Esc，等于被关在里面。
2. **测试是假阳性** —— `toastCount > 0` 只数 DOM 里 `.toast` 的数量，不看 visibility/opacity。元素被 `visibility:hidden` 藏着照样算"通过"。我上一轮报告里那条「受限环境降级 → 有提示 ✓」**实际没验证到用户看得到**。

## 1.2 修复

**CSS**：`.toasts` 移出隐藏组。它是**全局浮层**，不属于"编辑界面 UI"，隐藏它没有道理。另外给它加了一套深色皮肤（半透明 + 模糊），与控制条同一套语言 —— 否则浅色系统主题下会在深色舞台上弹出刺眼的白面板。

**文案**：两条降级提示都补上了「按 Esc 退出展示模式」：

```
伪全屏模式      → 界面已铺满窗口，浏览器地址栏无法隐藏；功能完全一致。按 Esc 退出展示模式
已切换为伪全屏  → 浏览器拒绝了全屏请求，已切换为伪全屏；按 Esc 退出展示模式
```

**测试**：断言从"数数量"改成"查真实可见性"：

```js
// 容器与 toast 自身都不能被 hidden/transparent，且必须有真实尺寸
// （visibility:hidden 时 getBoundingClientRect 仍有值，所以尺寸要配合 visibility/opacity 判断）
s.toastContainerVis === 'visible' && Number(s.toastContainerOpacity) > 0.5
s.toastBoxH > 20 && s.toastVis === 'visible' && Number(s.toastOpacity) > 0.5
```

**新增反向断言**：原生全屏下不弹任何提示（防止删掉隐藏组后反而多弹东西）。

## 1.3 「这条测试在修复前会红」的实证

我把修复回退后重跑：

```
回退修复1 后（应看到 toast 可见性断言变红）
  ✗ 【关键】提示浮层在展示模式下**真实可见**（容器未被隐藏）  → visibility=hidden, opacity=0
  ✗ 【关键】提示本身有真实尺寸且可读  → h=79px, visibility=hidden, opacity=1
  ✓ 旧断言「toastCount > 0」                              ← 仍然通过，证实是假阳性
```

**旧断言在 bug 存在时依然通过，这正是假阳性的定义。** 新断言如实变红。

# 二、伪全屏下 F11 进出连带退出演示模式

## 2.1 根因

```js
function onFullscreenChange() {
  isNativeFullscreen.value = nativeActive()
  if (!isNativeFullscreen.value && isPresenting.value) {
    leavePresentation({ skipNativeExit: true })
  }
}
```

只要"原生全屏元素变空"就退展示模式。伪全屏状态下（`isPresenting=true, isNative=false`），用户按 F11 进原生全屏再按 F11 退出，第二次就触发退出 —— 但他**只想退出浏览器全屏**，并不想退出演示。更糟的是伪全屏是**永久状态**，这次误退出会让用户莫名回到编辑界面。

## 2.2 修复：用 `requestedNative` 标志区分"谁请求的"

按你建议的方向实现（不靠猜测）：

```js
/** 原生全屏是否是**我们自己请求的** */
let requestedNative = false

// enterPresentation 里
requestedNative = ok                 // 原生分支
requestedNative = false              // 降级分支（从未请求过）

function onFullscreenChange() {
  if (!requestedNative) {
    // 伪全屏：用户自己 F11 进出与我们无关，只同步状态、不退出演示
    isNativeFullscreen.value = nativeActive()
    return
  }
  isNativeFullscreen.value = nativeActive()
  if (!isNativeFullscreen.value && isPresenting.value) {
    leavePresentation({ skipNativeExit: true })
  }
}
```

`leavePresentation` 里**先清标志再退出原生全屏** —— 否则 `exitNative` 触发的 `fullscreenchange` 会被误当成"我们自己请求的被退出"，多走一次收敛逻辑。

## 2.3 「这条测试在修复前会红」的实证

```
回退修复2 后（F11 场景 A 应变红，场景 B 仍绿）
  ✗ 【关键】场景A：F11 退出原生全屏后**仍在展示模式**  → isPresenting=false
  ✗ 场景A：退出后回到伪全屏（仍是只剩歌词）
  ✗ 场景A：界面仍是展示模式（顶栏隐藏）
  ✓ 【不回归】场景B：F11 退出原生全屏 → 跟着退出演示模式   ← 仍绿
  ✓ 场景B：退出后顶栏恢复（没有卡在"UI 全没了"）
```

**场景 A 变红、场景 B 保持绿** —— 证明修复只针对你报告的路径，没有回归原有行为。

# 三、ensureHueVisible 在 S=6/7 跳变

按你确认的**方案 A（15→6）**实施。动手前先做了影响分析，结论如下。

## 3.1 对 1.3 设计意图的影响：无破坏，甚至强化

| 项 | 结论 |
|---|---|
| 「饱和度保持 15 不被拉满」 | 目标值 15 → 6，颜色只会**更淡**，不会更艳 |
| 纯白/黑显色 | 仍能显色，但需要把 S 按需提到 15（见 3.3） |
| 彩色不动 | 完全保留 |

## 3.2 实施中发现的一个真问题：两个阈值必须解耦

原先 `MIN_VISIBLE_CHROMA` 是由 `MIN_VISIBLE_SATURATION` **导出**的（`15 × 0.4 = 6`），靠"两个阈值恰好相等"保证亮度只被拉到边界。

把饱和度下限降到 6 之后，导出值变成 **2.4** —— 纯白只有 RGB 通道差 **6 级**，远低于肉眼可辨的 15 级，**等于把补丁 6 修好的显色能力又弄丢了**（7 项单测立刻变红抓到了它）。

结论：两个阈值管的是不同的东西，不能互相推导：

```
MIN_VISIBLE_SATURATION  管"饱和度被拉高到哪" → 影响跳变小不小  → 要小（6）
MIN_VISIBLE_CHROMA       管"色相可见不可见"     → 影响显不显色    → 要大（6%，=15 通道差）
```

现在各自独立取值，`MIN_VISIBLE_CHROMA = 6 - 1e-9`（epsilon 吸收浮点下溢，方向仍是**下调**，见补丁 5 记录）。

## 3.3 实施中测试抓到的第二个真 bug：亮度被过度调整

改完跑测试，`L=45` 竟然被拉到 **20** —— 为了 0.6 的色度差，把亮度砍掉 25 个百分点。

根因是第 2 步的写法是"朝可见区间**边界**拉"：

```js
const target = l > VISIBLE_L_MAX ? VISIBLE_L_MAX : VISIBLE_L_MIN   // ← 问题在这
```

修正为**朝 L=50（亮度因子最大、色度最大、最省力）走，且不超过可见边界就停手**：

```
s=0  l=100 (纯白) → S:15  L:80   ← 仍是亮色，chroma 6.00 ✓
s=0  l=0   (纯黑) → S:15  L:20   ← 仍是暗色 ✓
s=0  l=45  (中暗) → S:6.6 L:46   ← 只挪 1%，几乎不动 ✓
s=0  l=50  (正中) → S:6   L:50   ← 完全不动 ✓
```

**纯白的结果（S:15, L:80）与补丁 6 完全一致**，即 `#c4ccd4`。这保证了补丁 8 不会改变你在真机上已确认过的效果。

## 3.4 新增的 S∈[3..10] 逐点断言（你要求的）

固化了一张契约表，改 `MIN_VISIBLE_SATURATION` 会让它变红：

```
输入 S → 输出 S     0→6  1→6  2→6  3→6  4→6  5→6 │ 6→6  7→7  8→8  9→9  10→10 │ 11→11 … 15→15
```

并断言**拉伸区内不允许出现跳变**：`S≥6` 必须原样保留，`S<6` 必须一律拉到 6 —— 绝不允许出现"7 保留而 5 被拉成 15"这种割裂。

另加一条**取值依据的论证测试**：下限 6 在 L=50 时通道差正好 15 级（`#788087`），达到肉眼可辨下限；若将来有人想调得更低（S=3 → 差 7 级），这条会拦住他。
