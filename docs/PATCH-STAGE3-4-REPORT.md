## 一、按你的顺序：先回答"4 个怀疑方向里哪个最可能"

**我的判断：③ `preventDefault` 最可能 —— 但更准确的根因是「文本选择拖拽」，它正是 `pointercancel` 的触发者。**

你抓到的日志是决定性的，我逐条对应：

| 你抓到的现象 | 说明 |
|---|---|
| 第 2 次 `pointerdown` **到了**（clientX=1327, target=seek-knob） | 不是"浏览器吞掉事件" → **排除方向 ①（隐式捕获需要释放）** |
| `pointermove` #1/#2/#3 **也到了 window**（1326/1324/1323） | 事件通路完好 → 排除"事件被定向到别处"（②的前提不成立） |
| 收尾 `mode='cancel'`、`clientX=0` | 浏览器**主动**取消这次指针交互 |
| **之后 window 不再收到任何 pointermove** | 关键！指针被浏览器**独占**了 |

**"完全收不到 move"只有一种解释：指针被独占。** 而浏览器独占鼠标指针的机制只有一个 —— **原生拖拽**。鼠标下最常见的触发方式就是**文本选择拖拽**。

### 完整链条（解释"为什么第二次会触发、第一次不会"）

1. 进度条**右端之后是可选中的文本**：时长 `0:32`、倍速 `1×`、`模拟时钟` 徽标
2. 第一次**快速**拖动从 `clientX=115` 一路甩到 `1327` → 指针**扫过了这些文本** → 浏览器把这段文字**选中**了
   （**慢速拖动时 thumb 一直跟着指针**，指针始终停在轨道/旋钮上，没有扫过任何文本 → 没有产生选区 → 所以**慢速路径一切正常** —— 与你的观察完全吻合）
3. 松手后**选区残留**
4. 第二次 `pointerdown` 落在 `clientX=1327` —— **正好落在刚才被选中的文本上**
   在已选中的内容上按下鼠标，浏览器的行为是「**拖动这段选区**」
5. 移动 3 次（超过 Chrome 的拖拽启动阈值）→ 浏览器接管指针 → `pointercancel` → 独占

### 为什么笔/触摸免疫 —— 决定性佐证

Pointer Events 规范原文：*"If the event is pointerdown, the associated device is a **direct manipulation device** … then set pointer capture (implicit pointer capture)"*。

**笔和触摸是 direct manipulation device**，浏览器自动施加**隐式捕获** → 捕获状态下不会启动选择拖拽 → **没有选区残留** → 永远不触发。
你"换数位板立刻正常"正是这个机制的直接体现。

> 顺带修正我上轮的一个说法：我曾按规范推断"隐式捕获只给触摸/笔、不给鼠标"，因此判断你说的"鼠标独有隐式捕获"方向反了。但你的实测（鼠标坏/笔好）与这条机制**在结果上完全一致** —— 只是"导致差异的原因"是"笔有隐式捕获所以不会产生选区残留"，而不是"鼠标有隐式捕获所以会卡"。

### 为什么 ③ 优于 ②（重新加捕获）

`setPointerCapture` 只是**重定向**后续指针事件；而文本选择/拖拽的启动由**兼容 mouse 事件**（mousedown→mousemove）驱动，重定向不必然阻止它。
`preventDefault()` 则是规范**明文规定**的确定性手段：

> *"Authors can prevent the firing of certain compatibility mouse events by canceling the pointerdown event … This sets the **PREVENT MOUSE EVENT** flag on the pointer."*

取消 `pointerdown` → 兼容 mouse 事件**完全不发** → 没有 `mousedown` → 浏览器**无从启动**选择/拖拽 → `pointercancel` 的触发条件被从源头消灭。

### 其余两个方向的评估（未采用，理由如下）

| 方向 | 评估 |
|---|---|
| ①（若 pointerdown 没触发→主动释放隐式捕获） | 前提不成立：你的日志证明 pointerdown **有**触发 |
| ④（`draggable="false"`） | 进度条上没有 `<img>`/`<a>`/`<input>` 这类原生可拖拽元素，`draggable` 属性只影响它们；文本选择由 `user-select` 管。**已作为纵深防御顺手加上 `user-select: none`**（成本一行），但主修复是 ③ |
| ②（pointerdown 里 `setPointerCapture` 再立即 release） | "听起来怪但有效"的说法通常针对**旧版 Chrome 的捕获状态残留**；我们的代码已无任何捕获调用，无状态可清。**未采用**，避免引入无依据的巫术代码 |

## 三、防卡死体验（你要求的"取消后无感续接"）

即使未来出现无法穷举的 `pointercancel` 原因，用户也不该感觉"卡住"：

**实现**：`pointercancel` 后开一个 **200ms 观察窗**；用户若在这段时间内继续移动指针，回调 `onResume` → `PlayerBar` 以那个事件为起点**重新调用 `startSeekDrag`** → 无缝继续拖动。

```
pointerdown → 拖动中 → pointercancel（无法避免）
                          └→ 200ms 内用户继续移动 → onResume → 新会话无缝续接
                          └→ 超过 200ms 无移动   → 视为"用户真的松手了"，不再触发
```

200ms 取值：覆盖"浏览器取消 → 用户手还没停"的间隙，又短到不会把"用户真松手后随意晃鼠标"误判成继续拖动。
